## OWASP MCP Top 10

Every finding carries both a rule id (`AS-006`, `AV-001`) and one of ten OWASP MCP categories,
so a rule result and a scanner result read the same way, and the same categories appear
identically in the CLI, the hook, and the dashboard.

| Code | Category |
|---|---|
| MCP01 | Token Mismanagement & Secret Exposure |
| MCP02 | Tool Poisoning (Hidden Instructions) |
| MCP03 | Cross-Origin Escalation / Tool Shadowing |
| MCP04 | Rug Pull (Tool Drift After Install) |
| MCP05 | Command Injection, Path Traversal, SSRF, File Access |
| MCP06 | Missing/Weak Authentication |
| MCP07 | Supply Chain / Malicious or Typosquatted Dependencies |
| MCP08 | Prompt Injection via Live Tool Responses |
| MCP09 | Excessive Agency / Overprivileged Scope |
| MCP10 | Weak/Missing Audit Logging |

**MCP08 is never tested by a static scan.** It requires dynamic, adversarial testing against a
server's actual runtime tool responses, which is out of scope for this version. Every report includes an
explicit note saying so, rather than silently omitting it. It is a documented gap, not a clean result.

## Risk score and grade

**Risk counts up.** 0 is clean; 100 is "do not use". Each finding adds points by severity:

| Severity | Risk points |
|---|---|
| Critical | 25 |
| High | 15 |
| Medium | 8 |
| Low | 2 |
| Info | 0 |

The total is capped at 100, so volume cannot out-rank severity: a server with forty low-severity
findings cannot score worse than one with a live remote-code-execution hole. A grouped finding
still counts once per affected tool, because grouping is how the report is presented, not a
discount.

The letter comes from the number:

| Risk | Grade | Meaning | Suggested policy |
|---|---|---|---|
| 0-9 | **A** | Trusted | ALLOW |
| 10-24 | **B** | Generally safe | ALLOW |
| 25-49 | **C** | Caution | REQUIRE_APPROVAL |
| 50-74 | **D** | High risk | REQUIRE_APPROVAL |
| 75-100 | **F** | Do not use | BLOCK |

The suggested policy is a recommendation, never an automatic action.

<Callout type="warn" title="The score changed direction">
If you used Aevrin before this change, the score counted **down** from 100, where higher was
better. It now counts **up**, where higher is worse. Scans from before the change show no score
rather than a converted one: the two numbers are not convertible, and inventing a conversion
would have been a lie about a security result.
</Callout>

## No grade is a real result

A scan gets **no letter at all** when any of these is true:

- A scanner that should have run did not (Docker down, a missing binary, no network).
- **No MCP tools could be enumerated.**
- The scan itself failed before it finished.

The second is the common case and the more dangerous one. Zero findings from a server whose
tools nobody could read looks exactly like a perfect server. Rather than print an A, Aevrin
prints `?`, labels it *Not graded*, and says why:

```text
Scan Incomplete

The server started but returned no tool definitions. The findings below are real, but they
do not add up to a complete security assessment, and no grade is given because there is
not enough evidence to justify one.
```

The first sentence names the stage that stopped the scan, because the three common ways a
scan ends early need three different answers from you:

| Stopped at | What it means | What to do |
|---|---|---|
| Resolving | No runnable MCP server could be identified. The target may be a library, a specification, or documentation rather than a server. | If it is a server, scan the command that starts it: `aevrin scan mcp "npx -y <package>"`. |
| Launching | The server was identified but would not start, so its tools were never read. | Run the same command yourself. A server that needs a credential or a config file before it completes the MCP handshake cannot be enumerated: the sandbox is given no environment of its own, so a scanned server never inherits one. |
| Enumerating | The server started and returned nothing. | Tools are probably registered through indirection that cannot be read. Registering them with literal names and descriptions, or publishing a manifest, makes them reviewable. |

Only the third is a statement about the server's tools. Reporting the other two that way
was a claim about a target the scan never reached.

A scan that **failed** is reported separately, and it says nothing about the target:

```text
Scan Failed

This scan did not finish, so it is not an assessment of this target. Any findings listed
below were recorded before it stopped and are real, but the checks that never ran could
have found more.
```

The distinction is deliberate. A failed run leaves no recorded tools behind, and reporting
that emptiness as "no tool definitions were found" would be a claim about the server that
the scan never established.

## Risk summary

Every report opens with the five things you actually need, generated from the findings that
drove the score rather than from a template:

```text
Needs Approval

Arbitrary Code Execution and Excessive Permissions raise enough risk that this server
should not be trusted automatically.

Potential impact:    Anything that can influence this tool's arguments can run code with
                     the MCP process's own permissions.
Recommended action:  Require approval for the tools named below, and re-scan once their
                     permissions are narrowed.
Suggested policy:    REQUIRE_APPROVAL
```

Ranking is by the risk each rule actually contributed, not by how many times it fired: a server
with one critical execution hole and twenty-four informational notes is about the execution hole.

## Incomplete scans

A scan category (credential exposure, supply chain) is marked **unreliable** when its scanner
fails to execute. Not when it runs and finds nothing, but when nothing ran at all.
Common causes: Docker isn't running, a scanner binary is missing, or the network is unreachable.
The CLI pins its scanner images and runs them sequentially with a 2 GB per-tool ceiling; Docker
Desktop should have at least 4 GB available. On Windows it must be using Linux containers and
permit bind mounts from the system temporary directory.

Runtime MCP inspection accepts only public HTTPS endpoints. Submitted stdio commands are never
executed by Aevrin, and private/loopback/link-local/metadata targets are rejected. When no safe
remote endpoint exists, tool-description coverage is shown as skipped rather than failed or
silently treated as clean.

If any category is unreliable, the whole scan is flagged `incomplete` and that status follows it
everywhere:

- The **CLI** prints a red warning, shows `?` instead of a letter, and exits with code `3`,
  regardless of `--fail-on`.
- The **hook** blocks the install with a `block_incomplete` decision instead of silently
  allowing. An empty findings list from a category that never ran is not evidence of safety.
- The **dashboard** shows a destructive-styled banner naming the specific categories that
  couldn't run, and the grade tile reads `?` / *Not graded* rather than a letter.

This is a deliberate, security-first design choice: a scanner that can be made to say "clean"
just by breaking its own tools isn't trustworthy. An incomplete result is always treated as
*inconclusive*, never as a pass.

## Self-reported results

The CLI runs every scanner **on your own machine** and reports the result to Aevrin's backend.
Aevrin does not re-run the scan server-side (that is not feasible for a local filesystem path, and
would be redundant for a public repo). This has one real security implication worth being
explicit about: **the risk score and grade are independently verified, the findings list is not.**

- **Risk score and grade**: both recomputed server-side from the findings you submit, using the
  exact same function the CLI used. A hand-crafted upload cannot claim a better letter than its
  own findings justify, and cannot claim any letter at all for a target whose tools it never
  enumerated. The client-submitted values are logged but never trusted for storage.
- **Findings**: not independently re-verified. A valid API key can, in principle, submit
  fabricated or incomplete findings. This is an inherent limitation of any tool that runs
  locally and reports centrally, the same shape as, for example, a CI badge driven by a
  self-reported test result. It's also why every scan on the dashboard is labeled *"self-reported
  by the scanning client, not independently re-verified by Aevrin"* rather than presented as an
  unconditional guarantee.

Every scan result carries this framing consistently: a real signal worth trusting for its
stated scope, not a cryptographic attestation.

## Target types

| Type | What it means | What runs |
|---|---|---|
| GitHub repo | A `github.com` URL | Full pipeline: clone, tool discovery, MCP rules, behavior analysis, credential exposure, supply chain |
| Local path | A directory on your machine (CLI only) | Same as above, minus cloning |
| Live server URL | A running MCP server's URL | Every tool rule, against the tools the server answers with. No source to read, so behavior analysis and the credential and supply-chain checks do not run |
| Pasted config | A `{"mcpServers": {...}}` JSON blob | Same as a live server URL, per declared server |

For repo and local-path targets, Aevrin first checks whether the target actually is an MCP
server (`@modelcontextprotocol/sdk`, `fastmcp`, the `mcp` PyPI package, a registration call, a
registry manifest). Naming a repository `mcp-something` is not evidence and does not count. If
it is not an MCP server, the scan stops there and says so: Aevrin does not audit general source
code, so there is nothing further for it to report.

## Quota and tiers

Quota resets on a **rolling monthly window from your signup date**, not the calendar month, and
is tracked independently across three buckets. CLI, hook, and dashboard scans each have their
own limit:

| Tier | CLI scans/mo | Hook scans/mo | Dashboard scans/mo | History retention | PDF export | AI review per scan |
|---|---|---|---|---|---|---|
| Free | 5 | 2 | 5 | 7 days | No | 40 findings |
| Hobby | 50 | 20 | 50 | 90 days | Yes | 200 findings |
| Pro | 200 | 100 | 200 | 1 year | Yes | 200 findings |
| Team | Usage-based | Usage-based | Usage-based | Unlimited | Yes | 200 findings |

AI review runs on every plan, capped per scan so one very large repository cannot consume an
unbounded budget. Paid plans use a stronger model. A scan that hits the cap says so, and reviews
its highest-severity findings first. See [AI review](/docs/results#ai-review) for what the review
does and does not affect.

Exceeding a bucket's limit returns a two-part message everywhere it can happen (CLI, hook,
dashboard): what happened, when it resets, and where to upgrade. Never a bare refusal.
