Aevrin scans [Model Context Protocol](https://modelcontextprotocol.io) (MCP) servers for
security risks before you trust them. Give it a repository, a local path, or a launch command,
and it starts the server, reads the tools it actually exposes, and runs a fixed set of MCP
security rules against them — then maps every result onto the
[OWASP MCP Top 10](/docs/concepts#owasp-mcp-top-10), so a finding means the same thing
everywhere it appears: in the CLI, in a Claude Code hook block, and on the dashboard.

Aevrin is **not** a general-purpose code scanner. It will not tell you about a SQL-injection bug
in an unrelated part of your repository, and it will not report Dockerfile style, CI
configuration, or repository badges as security findings. It answers one question: is this MCP
server safe to give an agent.

## The three ways to use it

<Cards>
  <Card title="CLI" href="/docs/cli">
    `aevrin scan <target>` runs every scanner locally and gives you a full report in your terminal.
  </Card>
  <Card title="Claude Code hook" href="/docs/hook">

  </Card>
</Cards>

## Quick start

```bash
pipx install aevrin
aevrin login
aevrin scan https://github.com/owner/mcp-server
```

See [Getting Started](/docs/getting-started) for the full walkthrough, including installing on
older Python versions and connecting the Claude Code hook.

## What a scan actually checks

A repository or local-path scan clones (or reads) the target and runs, in order:

1. **Tool discovery.** Confirms the target really is an MCP server, and reads the tools it
   exposes out of its own registration sites. If it is not an MCP server, the scan says so and
   stops.
2. **MCP tool rules.** Twenty-four rules over every discovered tool: tool poisoning, permission
   surface, scope mismatch, arbitrary code execution, privilege escalation, secret handling,
   typosquatting, tool shadowing, missing rate limits, compromised packages, install-time
   scripts, dangerous launch commands, and more. See [Rules and coverage](/docs/scanners).
3. **Supply chain**, scoped to the dependencies the scanned server itself exposes: known CVEs,
   confirmed-compromised package versions, install-time scripts and malicious indicators. Where a
   server exposes no dependency metadata, that is reported as limited coverage rather than
   treated as clean.

Your grade is the **worst tool's** grade, not an average. You install the whole server, and the
worst tool is the one that reaches your data. See [Concepts](/docs/concepts#target-types).

## Honesty over false confidence

Two things Aevrin is deliberately strict about, because a security scanner that can be tricked
into saying "clean" is worse than no scanner at all:

- **An incomplete scan gets no grade at all.** Not an A, not an F. If a scanner could not run, or
  if the server's tools could not be enumerated, the grade is `?` and the report says why. Zero
  findings from a server nobody could read looks exactly like a perfect server, so Aevrin
  refuses to print a letter for it.
- **Not everything is tested.** Prompt injection via a live tool's *runtime responses* (MCP08)
  requires dynamic, adversarial testing against a running server and is out of scope for static
  scanning. Every report says so explicitly rather than silently omitting it.

Read more in [Concepts](/docs/concepts).
