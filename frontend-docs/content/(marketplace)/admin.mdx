---
title: Registry administration
description: How administrators create, publish and retire registry items, what they cannot change, and what gets audited.
---

Administration lives at `/admin/marketplace` in the app, behind the same admin session and TOTP
checks as the rest of the admin panel. The admin panel is the only place anything is published.

## Lifecycle

| State | Visible publicly | Reached by |
| --- | --- | --- |
| Draft | No | Creating an item, a server synced from the official MCP Registry, unpublishing, restoring |
| In review | No | A user's suggestion |
| Published | Yes | **Publish**, which runs the publish check below |
| Suspended | No | Suspending a published item |
| Archived | No | Archiving. Restore returns it to draft, never straight to published |

**Delete** removes an item permanently. It asks you to type the item's slug first, and the audit
record is written before the item is removed.

## What an administrator can do

- Create an item of any type, by hand or from a GitHub URL (it starts as a draft)
- Edit title, description, author, publisher, categories, tags, technologies, capabilities, use
  cases, content (prompt, instructions, usage, documentation, examples, inputs and outputs),
  installation, repository and ref, pricing metadata, licence, homepage, visibility, and featured
- Relate items to each other ("uses" or "related")
- Publish, unpublish, suspend, archive, restore, delete
- Publish the registry drafts that meet a stated quality bar, in bulk (below)
- Refresh an item's GitHub and npm metadata
- Create and delete categories (a category in use cannot be deleted)
- Review suggestions and reports

The editor's **Preview** tab shows the item as the public page will, in any state, and lists
anything that would stop it being published.

## The publish check

Publishing is refused, with every reason listed, when:

- the title or description is missing;
- the type's required content is missing (a prompt's text, a skill's instructions, a repository's
  URL; see [the table on the overview page](/overview#what-an-item-is));
- the content or installation fails validation (for example, a package name that looks like a
  shell command, or an endpoint that is not public HTTPS).

There is no scan requirement: the registry is discovery only, and publishing is curation, not a
security verdict. The editor's **Install** tab has the same **Scan with Aevrin** action as the
public page, which opens your own scan of the server on the scan page; nothing about that scan is
recorded on the item.

## Applying the popularity bar

Every server synced from the official MCP Registry arrives as a draft, and keeps doing so. **Apply
popularity bar** on the registry admin page publishes, in one action, only the drafts that meet
a star bar you choose (50 by default), and sets every published MCP server known to be below it back
to draft. The preview shows how many drafts meet each common bar (1, 10, 25, 50, 100 and 500 stars),
so you can compare before choosing:

- a public MCP server that the registry sync added, still a draft (a draft an administrator created,
  or an organisation's private item, is never included);
- at least the chosen number of GitHub stars (a draft whose star count is not known yet does not meet
  it; a published server whose count is not known yet is left published);
- it passes the publish check above;
- it is the only listing for its repository: a draft whose repository already has a published
  listing is skipped, and of several drafts for one repository only the one with the most stars
  (then npm downloads, then the most recently updated) is published.

It always shows a preview first: the exact number that will be published and unpublished, the bar,
how many drafts stay drafts and why, and the most common reasons drafts fail the publish check. Nothing is written
until you confirm. At most 500 are published per run; if more qualify, the result says so and you
can preview the next batch. Each item published this way gets its own timeline entry and audit
record, and the run itself is recorded once more with the bar applied and the counts.

Star counts come from GitHub and are refreshed every hour for every server with a GitHub repository,
drafts included, so a newly synced server has a count within a few hours. A server with no GitHub
repository never has one, and so is published by hand rather than by the bar.

## What an administrator cannot do

**Change an item's status by editing it.** Status is not in the allowlist of editable fields: it
changes only through the lifecycle actions above, so every publish goes through the publish check.
The allowlist is an allowlist rather than a denylist, so a column added later cannot become writable
by being forgotten.

Changing an MCP server's version adds it to the item's version list.

A listing owned by an organisation cannot be made public, and a public listing cannot be made
private without one.

## Audit trail

Every administrative action is recorded in the admin audit log with the administrator, the action,
the item, and the time. Consequential changes are also recorded on the item's own public timeline:
visibility, status, pricing, licence, featured status, categories. Each entry carries the actor,
the before and after values, the reason, and the time.
