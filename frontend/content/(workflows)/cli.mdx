All commands print human-readable status to stderr and results to stdout, so `aevrin scan ... >
report.txt` captures just the report. Every command supports `--help`.

## `scan`

```bash
aevrin scan TARGET [OPTIONS]
```

Runs the full scan pipeline against `TARGET` and prints a report.

| Argument | Description |
|---|---|
| `TARGET` | A GitHub URL, a local directory path, or a live MCP server URL. Required. |

| Option | Default | Description |
|---|---|---|
| `--json` | off | Machine-readable JSON output instead of the terminal report. |
| `--upload` / `--no-upload` | `--upload` | Save the result to your dashboard. On by default when logged in. Pass `--no-upload` for a purely local, ephemeral scan (e.g. in CI, where you don't want scan history persisted). |
| `--fail-on SEVERITY` | `high` | Minimum finding severity that causes a non-zero exit code. One of `critical`, `high`, `medium`, `low`, `info`. |

**What gets checked depends on the target type:**

<Tabs items={['Source target', 'Live server']}>
  <Tab value="Source target">
    Full pipeline: cloning (repos only), static analysis, secrets, dependencies, then the tool
    description check. See [Introduction](/docs/#what-a-scan-actually-checks).
  </Tab>
  <Tab value="Live server">
    Only the tool description check runs, because there is no source to clone or scan statically. The
    URL itself becomes the entrypoint for MCP-Shield and the patched official MCP SDK. Live
    targets must use public HTTPS; local, private, metadata, and credential-bearing URLs are
    rejected to prevent SSRF.
  </Tab>
</Tabs>

**Exit codes:**

| Code | Meaning |
|---|---|
| `0` | Scan completed; no findings at or above `--fail-on`. |
| `1` | Scan completed; at least one finding at or above `--fail-on`. |
| `2` | Could not run at all: not logged in, quota exceeded, unreachable API, or an invalid target or flag. |
| `3` | Scan ran but is **incomplete**: a required tool category failed to execute (Docker not running, a missing binary, no network). This fires regardless of `--fail-on`, because an incomplete scan is never treated as a pass. See [Concepts → Incomplete scans](/docs/concepts#incomplete-scans). |

```bash title="Fail a CI job only on unresolved criticals, keep local scan history out of the dashboard"
aevrin scan . --fail-on critical --no-upload
```

The CLI uses version-pinned, disposable Linux containers. Keep Docker Desktop running with at
least 4 GB assigned, use Linux containers on Windows, and allow its temporary-directory bind
mounts. Current errors include a redacted scanner stderr excerpt, so an image-pull, mount,
network, timeout, or memory problem is distinguishable from a vulnerability finding.

## `login`

```bash
aevrin login
```

Starts the browser device-code flow and stores an API key at `~/.aevrin/credentials`. Running it
again while already logged in prints a warning and exits `0`. Run `aevrin logout` first to
switch accounts.

## `logout`

```bash
aevrin logout
```

Removes the stored CLI credentials. It does not affect the separate hook credentials. See
[`hook logout`](#hook-logout).

## `version`

```bash
aevrin version
```

Prints the installed version. Equivalent to the top-level `aevrin --version` flag.

## `hook setup`

```bash
aevrin hook setup
```

Logs in a **separate** credential (`~/.aevrin/hook_credentials`) for the Claude Code hook, then
prints a `.claude/settings.json` snippet pointing at the hook script bundled inside this exact
`aevrin` install, so there is nothing else to download or clone. See [Hook](/docs/hook) for the full setup
walkthrough and why hook and CLI usage are tracked separately.

## `hook logout`

```bash
aevrin hook logout
```

Removes the stored hook credentials.

## `hook allow`

```bash
aevrin hook allow TARGET
```

Grants a 10-minute override so the hook lets the *next* install of `TARGET` through despite
unresolved high or critical findings. This is the "install anyway" path. `TARGET` must match exactly what
the hook printed in its block message. This doesn't fix or dismiss the findings, it just doesn't
block on them once.

## `scan --remote`

```bash
aevrin scan ./my-project --remote
```

Scans a local folder on Aevrin's servers instead of on this machine. Every scanner is installed
there, so this needs no Docker and no scanner binaries locally, and runs tools that cannot run
here at all: semgrep has no native Windows build, and works over `--remote` from Windows.

The folder's source is uploaded. In a git repository the file list is `git ls-files --cached
--others --exclude-standard`, so whatever `.gitignore` excludes is excluded here too; otherwise
dependency directories, build output, and virtualenvs are pruned. `.git` is never sent, since its
history carries every secret that was ever committed and later removed. A 62 MB folder typically
packs to well under a megabyte of actual source.

The report is identical to a local scan, and the result is already on your dashboard because the
server produced it. The uploaded copy is deleted when the scan finishes, and nothing in it is
executed.

Only for local paths. A GitHub URL or a live MCP server is already reachable from Aevrin, so
scan those from the dashboard.

## `agent scan`

```bash
aevrin agent scan
aevrin agent scan --json
aevrin agent scan --project ./my-repo --verbose
```

Reports what the AI coding agents on this machine have been allowed to do: permissions, MCP
servers by scope, skills, plugins, hooks, and which credentials are within reach. Configuration is
read and nothing else — no agent is started, nothing from a config file is executed, and nothing
leaves the machine.

`--json` returns a versioned snapshot (`schema_version` `"1"`) that is stable across runs, so two
snapshots can be diffed. Credential **values** are never included; only that one is present and
where. See [AI agent posture](/docs/agent-posture) for what is discovered and how permissions are
resolved.

## `findings triage`

```bash
aevrin findings triage FINDING_ID STATUS [--reason TEXT]
```

Updates a finding's triage status. This is the "false report" path. `STATUS` is one of `open`, `fixed`,
or `false_positive`. False-positive reports require `--reason`; the reason and triage timestamp
are retained with the dashboard finding and exported report. Marking a finding `false_positive`
excludes it from future hook-blocking checks and open-risk summaries. `FINDING_ID` comes from a
hook block message or a `--json` scan's `findings[].id`.

```bash title="Dispute a finding the hook just blocked on"
aevrin findings triage 3fa85f64-5717-4562-b3fc-2c963f66afa6 false_positive \
  --reason "Generated test fixture; cannot authenticate against any environment"
```
